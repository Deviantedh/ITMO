# Commenting Guide

## Цель

Комментарии должны ускорять понимание кода, а не дублировать очевидное.
Их задача:

- быстро объяснить, что проверяет тест;
- кратко описать назначение класса или метода;
- зафиксировать важное поведение, инвариант или ограничение.

Если комментарий не добавляет новой информации, его не нужно писать.

## Основные правила

- Пишите комментарии только там, где они реально помогают читать код быстрее.
- Предпочитайте короткие формулировки: обычно одна строка, максимум 1-2 коротких предложения.
- Используйте нейтральный технический стиль без разговорных слов, шуток и черновых пометок.
- Пишите в настоящем времени: `Проверяет`, `Возвращает`, `Добавляет`, `Переводит`.
- Не пересказывайте реализацию построчно.
- Не оставляйте комментарии-заглушки вроде `TODO`, если за ними нет конкретного действия.

## Комментарии в тестах

Перед каждым `@Test` ставьте короткий однострочный комментарий формата:

```java
// Проверяет ...
```

Такой комментарий должен объяснять:

- какой сценарий покрывает тест;
- какую ветку, инвариант или исключение он проверяет;
- какой важный ожидаемый результат должен выполниться.

### Хорошие формулировки

```java
// Проверяет валидацию входных данных: null-массив недопустим.
// Проверяет полный сценарий из условия с порядком ключевых событий в журнале.
// Проверяет, что moveTo меняет локацию, состояние и пишет событие в журнал.
// Проверяет инвариант: толпа из одного участника не может ликовать.
```

### Плохие формулировки

```java
// Тест
// Проверка
// Тут проверяем метод
// Создаем объект и смотрим что будет
```

### Что важно для тестовых комментариев

- Комментарий должен быть конкретнее, чем название теста, или хотя бы быстро раскрывать его смысл.
- Если тест покрывает крайний случай, это нужно явно написать.
- Если тест проверяет исключение, нужно указать причину исключения.
- Если тест проверяет позитивный сценарий, это тоже стоит обозначать явно.

## Комментарии в прод-коде

Для классов и публичных методов используйте короткие JavaDoc-комментарии:

```java
/** ... */
```

Они должны объяснять назначение сущности, а не повторять код.

### Для классов

Комментарий к классу отвечает на вопрос: "что это за сущность и зачем она нужна?"

Примеры:

```java
/** Локация в мире: может иметь родительскую локацию и набор объектов. */
/** Журнал доменных событий в порядке их добавления. */
/** Базовый объект мира с именем и закрепленной локацией. */
```

### Для методов

Комментарий к методу отвечает на вопрос: "что гарантирует этот метод?"

Примеры:

```java
/** Добавляет событие. */
/** Возвращает неизменяемый список всех событий. */
/** Переводит толпу в состояние ликования. */
/** Перемещает персону в новую локацию и фиксирует событие. */
```

### Когда JavaDoc не нужен

- для очевидных приватных методов;
- для простых геттеров и сеттеров, если проект не требует единообразного документирования;
- для кода, где название уже полностью раскрывает смысл и комментарий ничего не добавит.

Если в проекте уже принят единый стиль JavaDoc для публичных методов, его нужно соблюдать последовательно.

## Чего делать не нужно

- Не писать комментарии ради количества.
- Не дублировать название метода почти теми же словами без дополнительного смысла.
- Не писать эмоциональные или разговорные фразы.
- Не использовать комментарии вместо хороших имен классов, методов и переменных.
- Не описывать очевидные действия:

```java
// Присваиваем значение переменной
// Вызываем метод
// Возвращаем результат
```

## Рекомендуемый шаблон

### Тест

```java
// Проверяет валидацию входных данных: пустая строка недопустима.
@Test
void shouldThrowWhenNameIsBlank() {
    ...
}
```

### Класс

```java
/** Сервис расчета итоговой стоимости заказа. */
public class PricingService {
    ...
}
```

### Метод

```java
/** Возвращает список активных пользователей в неизменяемом виде. */
public List<User> getActiveUsers() {
    ...
}
```

## Быстрая проверка качества комментария

Перед тем как оставить комментарий, проверьте:

- помогает ли он понять код быстрее;
- объясняет ли он смысл, а не механику;
- можно ли сделать его короче без потери смысла;
- не является ли он очевидным повтором имени метода или теста.

Если на эти вопросы нельзя ответить положительно, комментарий лучше убрать.
